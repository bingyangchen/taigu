# 0004 後台

## 目標

開發者被設成 superuser 之後，可以從設定頁進入 Taigu 的後台：在使用情況頁看到每天、7 天與 30 天的活躍人數、每天的新註冊人數，以及每個註冊週的留存；在訂閱頁看到每個試用開始月份的試用轉付費比例、目前各訂閱狀態的人數，以及每月付款成功的筆數與金額；在問題回報頁讀使用者送出的問題回報，並把處理完的回報標記成已處理。其他使用者看不到後台的入口，開啟後台的網址也只會看到 404 頁面。

## 範圍

- 要做：
  - 新增 `admin.md` 這份 spec，寫下後台的權限、入口、導覽、三頁的統計與問題回報的處理。
  - 開發者依 email 把使用者設成 superuser 或取消，也可以列出所有 superuser。
  - 設定頁只對 superuser 顯示後台的入口。
  - 開啟後台的頁面不記下使用紀錄。
  - 在 `ui-guidelines.md` 加上後台的例外，這一項在這個 plan 的 PR 裡一起改。
  - 把 roadmap 的「後台」拆成這個 plan、「問題回報通知」與「依平台分開的統計」三個階段，也在這個 plan 的 PR 裡一起改。
- 刻意不做的事：
  - 收到新的問題回報時送 Telegram 通知，以及每則問題回報自己的網址 `/admin/issue-reports/<id>`，這些留給 roadmap 的「問題回報通知」。
  - 不依平台分開統計，也不做 roadmap 列的實機測試，這些留給 roadmap 的「依平台分開的統計」。
  - 不改付款紀錄在帳號刪除時一併刪除的做法，這件事記進 roadmap 的「訂閱流程修正」。
  - Flutter app 不顯示後台的入口。

## 設計稿

- `design/admin-console.html`：後台三頁在有資料、載入中、沒有資料與載入失敗時的畫面，以及問題回報的展開、勾選按鈕與標記失敗。設定頁的「管理」區塊照現有的設定頁區塊畫，沒有另外畫設計稿。

## Spec 變更

### admin.md

新增這份 spec，frontmatter 的 `prefix` 是 `ADMIN`，標題是「後台」。

#### 開頭的說明

後台讓開發者知道有多少使用者在使用 Taigu、新使用者會不會持續使用，以及試用後有多少使用者付費訂閱，並處理使用者的問題回報。只有 superuser 能使用後台，後台在 `/admin` 底下分成三頁：使用情況頁 `/admin/usage`、訂閱頁 `/admin/subscriptions` 與問題回報頁 `/admin/issue-reports`。

#### ADMIN-R1 只有 Superuser 能使用後台

只有 superuser 能開啟 `/admin` 底下的頁面，也只有 superuser 能讀取或修改後台的資料。開啟後台或讀取後台的資料時，Taigu 依以下規則處理：

- Superuser 開啟 `/admin` 時，畫面換到導覽的第一頁，也就是使用情況頁 `/admin/usage`，瀏覽紀錄裡的 `/admin` 被使用情況頁取代。
- 已登入但不是 superuser 的使用者開啟 `/admin` 底下的網址時，Taigu 在原本的網址顯示 404 頁面（見 PUB-R5）。
- 已登入但不是 superuser 的使用者不經過畫面、直接送出讀取或修改後台資料的 request 時，Taigu 拒絕這個 request，回應跟 request 送到不存在的網址時相同，而且使用者的登入狀態不變。
- 未登入的使用者開啟後台的網址時，處理方式見 ACCT-R3。

- ADMIN-R1.1 Superuser 開啟後台
  - 前提：使用者是 superuser，已經登入。
  - 動作：開啟 `/admin`。
  - 結果：網址換成 `/admin/usage`，畫面顯示使用情況頁。
- ADMIN-R1.2 不是 superuser 的使用者開啟後台
  - 前提：使用者已經登入，不是 superuser。
  - 動作：開啟 `/admin/usage`。
  - 結果：網址維持 `/admin/usage`，畫面顯示 404 頁面，標題是「找不到頁面」。
- ADMIN-R1.3 不是 superuser 的使用者直接讀取後台的資料
  - 前提：使用者已經登入，不是 superuser。
  - 動作：不經過畫面，直接向 Taigu 送出讀取問題回報列表的 request，接著開啟設定頁 `/settings`。
  - 結果：Taigu 拒絕讀取問題回報列表的 request，不回傳任何問題回報，回應的 status code 與內容跟 request 送到不存在的網址（例如 `/api/does-not-exist`）時相同；設定頁照常顯示這位使用者的名字與 Email，使用者沒有被登出。
- ADMIN-R1.4 未登入時開啟後台
  - 前提：使用者是 superuser，沒有登入。
  - 動作：開啟 `/admin/usage`，畫面換到歡迎頁之後，用 Google 帳號登入。
  - 結果：畫面換到 `/admin/usage`，顯示使用情況頁。
- ADMIN-R1.5 取消 superuser 之後重新整理
  - 前提：使用者是 superuser，開著使用情況頁 `/admin/usage`，之後開發者取消了這位使用者的 superuser。
  - 動作：重新整理頁面。
  - 結果：網址維持 `/admin/usage`，畫面顯示 404 頁面。
- ADMIN-R1.6 Access token 過期之後操作後台
  - 前提：Superuser 在登入滿 30 天之前開著問題回報頁的「未處理」，最後換發的 access token 已經過期。
  - 動作：點一則問題回報的勾選按鈕。
  - 結果：畫面出現提示「已標記為已處理。」，這則問題回報從列表消失，superuser 沒有被登出。

#### ADMIN-R2 設定與取消 Superuser

開發者可以依 email 把 Taigu 的使用者設成 superuser、取消 superuser，以及列出所有 superuser 的 email。輸入的 email 找不到 Taigu 的帳號時，開發者看到錯誤訊息，Taigu 不改變任何帳號。使用者改綁 Google 帳號（見 ACCT-R11）之後仍是 superuser。

- ADMIN-R2.1 設成 superuser
  - 前提：Email 是 `dev@example.com` 的使用者不是 superuser。
  - 動作：開發者把 `dev@example.com` 設成 superuser，這位使用者再開啟 `/admin/usage`。
  - 結果：畫面顯示使用情況頁。
- ADMIN-R2.2 取消 superuser
  - 前提：Email 是 `dev@example.com` 的使用者是 superuser。
  - 動作：開發者取消 `dev@example.com` 的 superuser，這位使用者再開啟 `/admin/usage`。
  - 結果：畫面顯示 404 頁面。
- ADMIN-R2.3 Email 找不到帳號
  - 前提：沒有任何 Taigu 帳號的 email 是 `nobody@example.com`。
  - 動作：開發者把 `nobody@example.com` 設成 superuser。
  - 結果：開發者看到錯誤訊息，所有帳號的 superuser 都沒有改變。
- ADMIN-R2.4 列出 superuser
  - 前提：Email 是 `dev@example.com` 與 `ops@example.com` 的使用者是 superuser，其他使用者都不是。
  - 動作：開發者列出所有 superuser。
  - 結果：列出的 email 只有 `dev@example.com` 與 `ops@example.com`。
- ADMIN-R2.5 改綁 Google 帳號
  - 前提：使用者是 superuser。
  - 動作：使用者把帳號改綁到另一個 Google 帳號，再開啟 `/admin/usage`。
  - 結果：畫面顯示使用情況頁。

#### ADMIN-R3 設定頁的後台入口

Superuser 的設定頁 `/settings` 有「管理」區塊，裡面只有連到後台 `/admin` 的「後台」；不是 superuser 的使用者，設定頁沒有「管理」區塊。

- ADMIN-R3.1 Superuser 從設定頁進入後台
  - 前提：使用者是 superuser，已經登入。
  - 動作：開啟設定頁 `/settings`，點「管理」區塊的「後台」。
  - 結果：網址換成 `/admin/usage`，畫面顯示使用情況頁。
- ADMIN-R3.2 不是 superuser 的使用者開啟設定頁
  - 前提：使用者已經登入，不是 superuser。
  - 動作：開啟設定頁 `/settings`。
  - 結果：設定頁沒有「管理」區塊，也沒有「後台」。
- ADMIN-R3.3 從後台按上一頁回到設定頁
  - 前提：Superuser 在設定頁 `/settings` 點「管理」區塊的「後台」，畫面顯示使用情況頁。
  - 動作：按瀏覽器的上一頁。
  - 結果：網址換回 `/settings`，畫面顯示設定頁。

#### ADMIN-R4 後台的導覽

後台的每一頁都有導覽，列出「使用情況」「訂閱」「問題回報」三頁與「回到 Taigu」，目前所在的頁面在導覽上顯示成選取狀態，點「回到 Taigu」時畫面換到儀表板 `/`。有未處理的問題回報（見 ADMIN-R13）時，導覽的「問題回報」旁邊顯示未處理的則數；沒有未處理的問題回報時不顯示則數。後台的頁面不顯示 Taigu 的側邊欄與底部導覽列。

導覽在寬的視窗裡是左側的側邊欄，側邊欄可以收合成只剩圖示：收合時，指到圖示會顯示頁面的名稱，未處理的則數顯示在「問題回報」圖示的右上角。收合或展開的狀態記在這個瀏覽器裡，之後開啟後台時維持同樣的狀態，第一次開啟時是展開的。導覽在窄的視窗裡放在畫面上方，不能收合，也不受側邊欄收合狀態的影響，「回到 Taigu」只顯示房子的圖示（版面見 ui-guidelines.md 的「後台」）。

- ADMIN-R4.1 有未處理的問題回報
  - 前提：Superuser 已經登入，Taigu 有 3 則未處理與 2 則已處理的問題回報。
  - 動作：開啟使用情況頁 `/admin/usage`。
  - 結果：導覽的「使用情況」顯示成選取狀態，「問題回報」旁邊顯示 3。
- ADMIN-R4.2 沒有未處理的問題回報
  - 前提：Superuser 已經登入，Taigu 的問題回報都已經處理。
  - 動作：開啟使用情況頁 `/admin/usage`。
  - 結果：導覽的「問題回報」旁邊沒有顯示則數。
- ADMIN-R4.3 回到 Taigu
  - 前提：Superuser 開著訂閱頁 `/admin/subscriptions`。
  - 動作：點導覽的「回到 Taigu」。
  - 結果：網址換成 `/`，畫面顯示儀表板。
- ADMIN-R4.4 收合側邊欄
  - 前提：Superuser 在桌面瀏覽器上開著問題回報頁，側邊欄是展開的，Taigu 有 3 則未處理的問題回報。
  - 動作：點側邊欄頂端的收合按鈕，再把滑鼠移到「訂閱」的圖示上。
  - 結果：側邊欄只剩圖示，「問題回報」圖示的右上角顯示 3；滑鼠指到的圖示旁顯示「訂閱」。
- ADMIN-R4.5 再次開啟後台時維持收合
  - 前提：Superuser 在桌面瀏覽器上把側邊欄收合之後，關閉了後台的分頁。
  - 動作：在同一個瀏覽器裡再開啟 `/admin/usage`。
  - 結果：側邊欄是收合的。
- ADMIN-R4.6 收合之後把視窗拉窄
  - 前提：Superuser 在桌面瀏覽器上開著使用情況頁，側邊欄是收合的。
  - 動作：把視窗拉窄到導覽移到畫面上方，再拉寬。
  - 結果：視窗窄的時候，上方的導覽列出「使用情況」「訂閱」「問題回報」三頁的名稱；拉寬之後，側邊欄仍是收合的。
- ADMIN-R4.7 第一次開啟後台
  - 前提：Superuser 在這個桌面瀏覽器上從來沒有開啟過後台。
  - 動作：開啟 `/admin/usage`。
  - 結果：側邊欄是展開的。

#### ADMIN-R5 統計的計算方式

後台的統計都依下面的定義計算：

- 一天、一週與一個月都以台灣時間計算，一週從週一到週日。
- 使用者在某一天有使用紀錄（見 USAGE-R1），就算這一天活躍，不論使用紀錄是哪個平台，也包括沒有記下平台的使用紀錄。
- 使用者的註冊日是 Taigu 替這位使用者建立帳號（見 ACCT-R2）的那一天。
- 使用紀錄開始的那天，是 Taigu 所有使用紀錄裡最早的日期；Taigu 還沒有任何使用紀錄時，沒有使用紀錄開始的那天。
- Superuser 與白名單上的使用者照樣算進統計，例外見 ADMIN-R9。
- Taigu 在開啟頁面時用當下的資料計算統計，所以帳號已經刪除的使用者不算進任何一天的統計，包括帳號刪除之前的日子。

- ADMIN-R5.1 同一天在不同平台使用
  - 前提：Superuser 在 2026/12/10 開啟使用情況頁；使用者 A 在 2026/12/09 有網頁、PWA 與沒有記下平台的使用紀錄各一筆，其他使用者在 2026/12/09 都沒有使用紀錄。
  - 動作：看使用情況頁的每日活躍人數。
  - 結果：每日活躍人數是 1 人。
- ADMIN-R5.2 註冊日以台灣時間計算
  - 前提：使用紀錄開始的那天是 2026/12/01。Taigu 在 UTC 2026/12/08 17:30（台灣時間 2026/12/09 01:30）替使用者 B 建立帳號，2026/12/08 與 2026/12/09 都沒有其他人註冊。
  - 動作：Superuser 在 2026/12/10 開啟使用情況頁，看新註冊人數的圖。
  - 結果：2026/12/09 的新註冊人數是 1 人，2026/12/08 是 0 人。
- ADMIN-R5.3 帳號刪除之後
  - 前提：2026/12/01 只有使用者 A 與使用者 C 有使用紀錄，開發者在 2026/12/05 依使用者 A 的要求刪除了 A 的帳號。
  - 動作：Superuser 在 2026/12/10 開啟使用情況頁，看活躍人數的圖上 2026/12/01 的每日活躍人數。
  - 結果：2026/12/01 的每日活躍人數是 1 人。
- ADMIN-R5.4 Superuser 也算進統計
  - 前提：2026/12/09 只有一位 superuser 有使用紀錄。
  - 動作：這位 superuser 在 2026/12/10 開啟使用情況頁。
  - 結果：每日活躍人數是 1 人。

> 設計理由：沒有記下平台的使用紀錄照常算成活躍，而不是排除或併進同一天有平台的那一筆，因為活躍人數依使用者與日期去重，沒有記下平台的那一筆不會讓人數重複算；排除的話，使用者只用過舊版前端的那幾天，活躍人數會少算這位使用者。完整討論見 [0004](../plans/archive/0004-admin-console.md)。

#### ADMIN-R6 使用情況頁的摘要數字

使用情況頁最上方顯示四個數字：昨天的每日活躍人數（DAU）、到昨天為止 7 天的活躍人數（WAU）、到昨天為止 30 天的活躍人數（MAU），以及到昨天為止的累計註冊人數。N 天的活躍人數是這 N 天裡至少活躍一天的使用者人數。每個數字底下顯示這個數字比 7 天前同一天增加或減少多少人，人數後面都寫「人」：

- 增加時用紅色寫「▲ +」與增加的人數。
- 減少時用綠色寫「▼ −」與減少的人數。
- 沒有變化時寫「±0 人」。

三個活躍人數另有以下規則，累計註冊人數不受這些規則影響：

- Taigu 還沒有任何使用紀錄，或昨天早於使用紀錄開始的那天時，三個活躍人數的位置都只顯示「尚未開始記錄」。
- 7 天前同一天早於使用紀錄開始的那天時，三個活躍人數都不顯示增減。

> 設計理由：區間有一部分早於使用紀錄開始的那天時，摘要數字照常顯示，不另外標示，因為這只發生在使用紀錄開始後的前 30 天，活躍人數的圖也已經把這段期間標成資料不完整。完整討論見 [0004](../plans/archive/0004-admin-console.md)。

- ADMIN-R6.1 四個數字
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/11/01。使用者 A 在 2026/12/09 有使用紀錄，使用者 B 在 2026/12/09 與 2026/12/04 有使用紀錄，使用者 C 在 2026/12/04 有使用紀錄，使用者 D 在 2026/11/12 有使用紀錄，使用者 E 在 2026/11/01 有使用紀錄，其他使用者都沒有使用紀錄；到 2026/12/09 為止有 412 位使用者註冊。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：每日活躍人數是 2 人，7 天的活躍人數是 3 人，30 天的活躍人數是 4 人，累計註冊人數是 412 人。
- ADMIN-R6.2 今天的使用不算進摘要數字
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/11/01。2026/11/10 到 2026/12/10 之間，只有使用者 A 在 2026/12/09 與 2026/12/10 有使用紀錄，以及使用者 F 在 2026/12/10 有使用紀錄；到 2026/12/09 為止有 412 位使用者註冊，使用者 F 在 2026/12/10 註冊。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：每日活躍人數、7 天與 30 天的活躍人數都是 1 人，累計註冊人數是 412 人。
- ADMIN-R6.3 跟 7 天前相比減少
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/11/01，2026/12/02 的每日活躍人數是 5 人，2026/12/09 是 2 人。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：每日活躍人數底下用綠色寫「▼ −3 人」。
- ADMIN-R6.4 跟 7 天前相比沒有變化
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/11/01，2026/12/02 與 2026/12/09 的每日活躍人數都是 2 人。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：每日活躍人數底下寫「±0 人」。
- ADMIN-R6.5 昨天早於使用紀錄開始的那天
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/12/10。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：三個活躍人數的位置都顯示「尚未開始記錄」，累計註冊人數照常顯示人數與增減。
- ADMIN-R6.6 還沒有任何使用紀錄
  - 前提：Taigu 還沒有任何使用紀錄。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：三個活躍人數的位置都顯示「尚未開始記錄」，累計註冊人數照常顯示人數與增減。
- ADMIN-R6.7 昨天就是使用紀錄開始的那天
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/12/09，使用者 A 在 2026/12/09 有使用紀錄。
  - 動作：Superuser 開啟使用情況頁。

#### ADMIN-R9 試用轉付費

訂閱頁有試用轉付費表，依試用期開始的月份把使用者分批。現在在白名單上的使用者，以及 Taigu 沒有記下試用期的使用者，不算進任何一批。

> 設計理由：試用轉付費不算白名單上的使用者，雖然後台的其他統計都包括他們（見 ADMIN-R5），因為白名單上的使用者不用付費就能使用 Standard，算進試用人數只會讓轉換率隨開發者加進白名單的人數變低；白名單只記下目前誰在白名單上，沒有加入與移出的歷史，所以依現在的白名單判斷。完整討論見 [0004](../plans/archive/0004-admin-console.md)。

表格列出從最早有人算進的月份到本月的每一個月，新的月份排在上面，每一列顯示：

- 試用開始的月份。
- 試用人數：試用期在這個月開始、算進這一批的人數。
- 付款人數：這一批裡，第一次付款成功（見 BILL-R14）的時間不晚於試用期結束後 30 天的人數，在試用期間付款的使用者也算。試用期的結束時間一律用 Taigu 記下的結束時間，使用者在試用期間付款時也一樣。

- 狀態：這一批的結算時間是這個月最後一天的隔天 0 點再過 61 天（31 天的試用期加 30 天），在這個時間之前，這一批的付款人數還會變，所以狀態顯示「進行中」與「<結算時間前一天的月/日> 結算」；到了這個時間之後，狀態顯示「已結算」。這個月還沒過完時，結算時間也照同樣的方式計算。

### architecture.md

#### 後台

在「使用統計」一節後面新增這一節：

> ## 後台
>
> api-server 把後台的 endpoint 都放在 `/api/admin/` 底下，由 `api-server/main/admin_console/` 這個 app 處理，每支 endpoint 都用同一個權限檢查：先確認登入狀態，沒有登入時跟其他需要登入的 endpoint 一樣回 401（見 ACCT-R4），前端照常換發 access token 再重送；已經登入但不是 superuser 時回 404。
>
> > 設計理由：不是 superuser 時回 404 而不是 403，因為前端收到 403 時會把使用者登出，而且回 404 時，一般使用者看到的結果跟網址不存在時相同，看不出 Taigu 有後台。完整討論見 [0004](../plans/archive/0004-admin-console.md)。
>
> 使用者是不是 superuser，記在 `User` 從 Django 的 `AbstractUser` 繼承的 `is_superuser` 欄位，開發者用 management command `superuser` 依 email 設定、取消與列出 superuser。`me` 的回應帶有 `is_superuser`，前端用它決定要不要顯示後台的入口與頁面。
>
> > 設計理由：Superuser 不另外開資料表，也不用 Django admin，因為 `is_superuser` 已經在 `User` 上，api-server 也沒有啟用 Django admin（見「白名單」一節）。完整討論見 [0004](../plans/archive/0004-admin-console.md)。
>
> 前端的後台頁面用 lazy load 載入，所以一般使用者開啟其他頁面時不會載入或執行後台的程式碼；不過 service worker 照常 precache 後台的 chunk。
>
> > 設計理由：後台的 chunk 不排除在 precache 之外，因為 service worker 用 cache 裡的舊版 `index.html` 回應頁面載入，排除的話，前端每次上線新版之後，舊版頁面要求的舊版後台 chunk 已經不在 Cloudflare Pages 上，後台會載入失敗。完整討論見 [0004](../plans/archive/0004-admin-console.md)。
>
> 問題回報是否已處理記在 `IssueReport` 的 `handled_at` 欄位，這個欄位是空的時候代表未處理。
>
> 後台的統計在每次讀取時從 `daily_activity`、`User`、`BillingProfile`、`standard_whitelist` 與付款的資料表計算，不存每天的彙總數字。各訂閱狀態的人數讀的是 `BillingProfile` 記下的 `subscription_status` 與 `cancel_at_period_end`：`subscription_status` 是 `past_due` 的使用者一律算成扣款失敗，不看 `cancel_at_period_end`；沒有 `BillingProfile` 的使用者算成未訂閱。
>
> > 設計理由：統計不存成每天的快照，因為帳號只會由開發者依使用者的要求刪除，刪除後過去的數字跟著變小的影響不大，而且留存與試用轉付費是依時間分批，就算每天存下快照，帳號刪除之後各批的數字還是會變。完整討論見 [0004](../plans/archive/0004-admin-console.md)。

## 做法要點

- 新增 api-server 的 app `admin_console`，不叫 `admin`，因為 Django 內建的 `django.contrib.admin` 已經用了這個 app label。
- `me` 的回應新增 `is_superuser` 欄位，所以 prod 上的前端與 Flutter app 不受影響。前端比 api-server 早上線時，`me` 還沒有這個欄位，superuser 暫時看不到後台的入口，開啟 `/admin` 也只會看到 404 頁面。
- Migration 在 `issue_report` 新增可以是空值的 `handled_at`，所以舊版的 api-server 照常運作，既有的問題回報也都是未處理。
- 前端的後台頁面用 `React.lazy` 載入，service worker 照常 precache 後台的 chunk，`service-worker.ts` 不用改。
- 前端在後台的頁面不呼叫 `open-session`（USAGE-R1）。
- 後台不用 `HeaderForMain`、`Footer` 與 `MainSideBar`，也不依 `Util.isMobile` 選版面，版面照 `ui-guidelines.md` 的「後台」一節。
- 問題回報的內容「超過 4 行」要依畫面上實際顯示的行數判斷，例如比較截斷之後的高度與完整內容的高度，而這種判斷方式依賴瀏覽器的排版。實作要讓只要內容被截斷，按鈕就是「展開全文與 User-Agent」，並把實測的瀏覽器行為記進 `architecture.md`。
- `daily_activity` 只有 `(user, date, platform)` 的 unique index，統計依日期查詢時會讀過整張表。目前資料量小，實作時如果查詢明顯變慢，再加上 `date` 的 index。
- 法律頁面不用改：隱私權政策已經寫明 Taigu 用個人資料「統計本網站的使用情況」，也寫明會記下問題回報的內容、平台與 User-Agent。
