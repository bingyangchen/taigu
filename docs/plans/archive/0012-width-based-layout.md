# 0012 依可用空間切換前台版面

## 目標

前台依可用空間切換版面，不再依 User-Agent 判斷裝置。手機不論直立或橫放都用頁首、底部導覽列與窄版的頁面；平板與縮小的桌面視窗用收合成圖示列的側邊欄與寬版的頁面；可用寬度至少 960px 時，側邊欄照現在的方式展開或收合。桌面瀏覽器的視窗縮到多窄都有導覽可用，iPad 的使用者也能點清單的一列開啟紀錄、買賣計畫與手續費折讓的編輯器。

## 範圍

- 要做：
  - 前端依 NAV-R2 在窄版、寬版且可用寬度小於 960px、可用寬度至少 960px 三種情況切換導覽。
  - 把依 `Util.isMobile` 決定的畫面都改成依窄版或寬版決定，例如編輯器開成編輯頁還是視窗、加號選單、搜尋、問題回報、市場頁的列表與卡片、個股詳情頁的工具列與按鈕、手續費頁的返回按鈕、設定頁的 bottom sheet 與對話框、圖表的資料點大小，以及用途字級。
  - 側邊欄收合成圖示列時，點「新增」開啟三種新增的選單（REC-R10）。
  - 清單的一列依 REC-R9 與 REC-R11 處理：點一列開啟編輯器，只有窄版的觸控裝置能長按，拿掉滑鼠移入時的編輯按鈕，只留刪除按鈕。歷史紀錄頁、買賣計畫頁與手續費頁的清單都照這個方式。
  - 個股詳情頁在觸控裝置上都能滑動換股，寬版，或能用滑鼠移入的裝置顯示左右箭頭（STOCK-R16）。
  - 歡迎頁與設定頁的法律頁面連結依是不是 PWA 決定在新分頁還是同一個畫面開啟（PUB-R3）。
  - 寬版的問題回報視窗有內容時，關閉之前先顯示「捨棄變更？」（ISSUE-R6），修正 `main` 上按 Esc 會丟掉內容的問題。
  - 移除 `Util.isMobile`，以及沒有任何頁面使用的 `TradeVolumeBarChart`。
  - `desktop-sidebar.md` 改名為 `navigation.md`，`tests/manual/desktop-sidebar.md` 一起改名為 `tests/manual/navigation.md`，prefix 維持 `NAV`。
  - 這個 plan 的 PR 已經依開發者的要求改好 `ui-guidelines.md`：「版面」改成依可用空間分成窄版與寬版、字級的設計理由改成說明用途字級為什麼在窄版與寬版的分界切換，以及「支援使用者放大文字與頁面」補上不提供雙指縮放整個畫面。
- 刻意不做的事：
  - 後台的版面維持 `ui-guidelines.md`「後台」一節的 780px 切換方式。
  - 頁面內容排列的寬度切換點維持原樣，例如大盤指數頁的兩張圖在 960px 改成並排、市場頁的卡片在 780px 排成多欄。
  - 不替 600 到 959px 另做一種頁面內容。
  - 視窗在編輯器開著時跨過窄版與寬版的分界，已經開啟的編輯器視窗或編輯頁維持原樣，這個行為不寫進 spec。

## 設計稿

無。這個 plan 沒有新的畫面：窄版的每一頁沿用現在行動裝置的版本，寬版的每一頁沿用現在桌面瀏覽器的版本，寬版且可用寬度小於 960px 時的側邊欄沿用 NAV-R1 收合後的樣子。實作照 sdd「Procedure: Implement」第 6 步，先讓開發者在可用寬度 768px 與 600px 時調整版面，再進 code review。

前台依版面（見 ui-guidelines.md 的「版面」）切換導覽：窄版用底部導覽列，寬版用側邊欄。可用寬度至少 960px 時，使用者可以把側邊欄收合成圖示列，前端保留使用者在目前瀏覽器選擇的收合狀態。

#### NAV-R1 桌面側邊欄收合與固定位置

需求的名稱改成「NAV-R1 側邊欄的收合與固定位置」。

收合功能只在寬版且可用寬度至少 960px 時提供，可用高度小於 480px 的視窗算窄版；有側邊欄的頁面改成 NAV-R2 列出的頁面，設定頁不在其中。以「在可用寬度至少 960px 的前台頁面」開始的那一段改成：

在 NAV-R2 列出的頁面，寬版且可用寬度至少 960px 時，側邊欄預設展開，寬度為 230px。使用者可以用側邊欄頂端的按鈕收合或展開側邊欄；收合時寬度為 64px，只顯示圖示，所有導覽與操作仍可使用，圖示也有 screen reader 可讀的名稱，滑鼠移入或鍵盤焦點停留時會顯示名稱 tooltip。按鈕能以鍵盤操作，並以 `aria-expanded` 表示目前狀態。

側邊欄固定在視窗左側的規則也適用於 NAV-R2 的圖示列。以「桌面前台的主內容捲動時」開始的那一段改成：

寬版的主內容捲動時，側邊欄固定在視窗左側，不隨主內容上下移動。側邊欄內容超出可用高度時，使用者可以獨立捲動側邊欄。

其他寬度的導覽改由 NAV-R2 規定。以「可用寬度小於 960px 時不顯示收合按鈕」開始的那一段改成：

窄版，或寬版且可用寬度小於 960px 時，導覽依 NAV-R2，不顯示收合按鈕，前端也不改寫收合狀態。

既有的其他情境與設計理由不變，修改以下情境：

- NAV-R1.6 窄版的導覽不受收合狀態影響
  - 前提：使用者已在同一個瀏覽器收合側邊欄，以 390 × 844 的可用畫面開啟前台。
  - 動作：開啟儀表板 `/`，再把可用畫面改成 1280 × 800。
  - 結果：390 × 844 時畫面顯示底部導覽列，沒有側邊欄與收合按鈕；改成 1280 × 800 後，側邊欄是收合的。
- NAV-R1.7 收合功能的最小可用寬度
  - 前提：使用者在可用寬度至少 960px、可用高度至少 480px 的視窗展開側邊欄。
  - 動作：把可用寬度縮到 959px，再拉回 960px。
  - 結果：959px 時側邊欄依 NAV-R2 收合成 64px 的圖示列，沒有收合按鈕；拉回 960px 時，側邊欄恢復展開，頂端有收合按鈕。

- NAV-R2.1 手機直立
  - 前提：使用者以 390 × 844 的可用畫面開啟前台。

> 設計理由：寬版且可用寬度小於 960px 時，側邊欄只顯示圖示，偏離 ui-guidelines.md「主導覽有可見文字」的預設，因為這一列跟可用寬度至少 960px 時使用者收合的圖示列相同，所以視窗寬度跨過 960px 時，導覽的圖示與位置都不變；而且這些圖示跟底部導覽列與展開的側邊欄用的是同一組，使用者在其他寬度可以看到這些圖示的名稱。不採用 Material Design 3 那種圖示下方附名稱、寬約 80px 的 navigation rail，因為那樣導覽會在三種樣子之間切換。這段寬度也不展開成 230px 的側邊欄，因為可用寬度是 600px 時，內容只剩 370px，比手機直立還窄。完整討論見 [0012](../plans/archive/0012-width-based-layout.md)。

#### REC-R11 編輯頁

開啟編輯頁還是編輯器視窗改成依窄版與寬版決定，而且在每個寬度點一列都開啟這筆紀錄的編輯器。規則改成：

編輯頁的網址是 `/records/trade/new`、`/records/trade/<紀錄 id>/edit`、`/records/cash-dividend/new` 或 `/records/cash-dividend/<紀錄 id>/edit`。在窄版，每一個新增與編輯紀錄的入口都開啟編輯頁；在寬版，入口開啟編輯器的視窗，不過連到這些網址的入口與直接開啟這些網址也顯示編輯頁。

使用者在歷史紀錄頁點一列時，前端開啟這筆紀錄的編輯器；在窄版的觸控裝置上，長按一列後點「編輯」也一樣。

修改以下情境：

- REC-R11.1 在窄版點歷史紀錄頁的一列
  - 前提：使用者有一筆交易紀錄，以窄版開啟歷史紀錄頁。
  - 動作：點這一列。
  - 結果：畫面換到網址是 `/records/trade/<這筆紀錄的 id>/edit`、標題是「編輯交易紀錄」的編輯頁，欄位帶入這筆紀錄的內容。

新增以下情境：

- REC-R11.2 在寬版點歷史紀錄頁的一列
  - 前提：使用者有一筆交易紀錄，以寬版開啟歷史紀錄頁。
  - 動作：點這一列。
  - 結果：歷史紀錄頁上方出現標題是「編輯交易紀錄」的編輯器視窗，欄位帶入這筆紀錄的內容，網址的路徑仍是 `/records`。

新增設計理由：

> 設計理由：在每個寬度點一列都開啟編輯器，因為寬版原本只能在滑鼠移入一列時按編輯按鈕，iPad 這類寬版的觸控裝置沒辦法用滑鼠移入，就沒辦法從列表編輯紀錄；點一列就能開啟編輯器之後，編輯按鈕也拿掉。長按只留在窄版的觸控裝置，因為長按後出現的 bottom sheet 是給手機單手操作設計的；寬版的觸控裝置不能長按，不過仍可以從編輯器的「其他操作」刪除紀錄。完整討論見 [0012](../plans/archive/0012-width-based-layout.md)。

## 決策

### 範圍要不要一併做平板寬度的導覽

- 選項：
  - 只把 User-Agent 判斷改成 960px 的寬度判斷，平板寬度的導覽留給之後的 plan。
  - 一次做完三種導覽。
- 取捨：只改成 960px 時，iPad 直立會先從側邊欄變成底部導覽列，之後再改成圖示列。
- 結論：一次做完三種導覽，並一起修改 `ui-guidelines.md` 的「版面」。
- 併入：無

### 窄版的分界

- 選項：
  - 窄版是可用寬度小於 960px，600 到 959px 用圖示列配上手機的頁面。
  - 窄版是可用寬度小於 600px。
  - 窄版是可用寬度小於 600px，或可用高度小於 480px。
- 取捨：窄版只看可用寬度小於 600px 時，手機橫放的寬度落在 600 到 959px，會拿到編輯器視窗，高度卻只有 400px 左右；窄版到 959px 時，600 到 959px 同時有側邊欄的「新增」與加號選單，iPad 直立也會用到同一時間只展開一段、為手機鍵盤設計的編輯頁（REC-R21）。
- 結論：窄版是可用寬度小於 600px 或可用高度小於 480px，其他都是寬版，頁面內容只分這兩種版本。
- 併入：ui-guidelines.md 的「版面」（這個 plan 的 PR 已經寫入）

### 寬版且可用寬度小於 960px 時的側邊欄

- 選項：
  - 沿用 NAV-R1 收合後 64px、只有圖示的一列。
  - Material Design 3 的 navigation rail，圖示下方附名稱。
  - 展開成 230px 的側邊欄。
- 結論：沿用 64px 的圖示列，在 spec 記錄這是「主導覽有可見文字」的例外。
- 併入：navigation.md#NAV-R2

### 圖示列上怎麼選三種新增

- 選項：
  - 點「新增」圖示就開啟三種新增的選單。
  - 在圖示旁邊另外放一個打開選單的小箭頭。
- 取捨：小箭頭在 64px 寬的圖示列上做不到觸控裝置要求的 44 × 44px。
- 結論：圖示列上點「新增」就開啟選單，可用寬度至少 960px 時使用者自己收合的側邊欄也一樣，所以 `main` 上收合後只能新增交易紀錄的問題一起修好。
- 併入：records.md#REC-R10

### 清單的一列怎麼編輯與刪除

- 選項：
  - 只看寬度：窄版點一列開編輯頁、長按叫出 bottom sheet，寬版滑鼠移入才顯示編輯與刪除按鈕。
  - 版面決定開成編輯頁還是視窗，輸入方式決定怎麼叫出操作。
  - 每一列常駐一個「更多」按鈕，拿掉長按與滑鼠移入。
- 取捨：只看寬度時，iPad 與只用鍵盤的使用者沒辦法從清單編輯或刪除；常駐按鈕會讓手機的清單變擠，也改到手機現在的操作。
- 結論：每個寬度點一列都開啟編輯器，窄版的觸控裝置可以長按，能用滑鼠移入的裝置顯示刪除按鈕，拿掉編輯按鈕。
- 併入：records.md#REC-R11

### 法律頁面的開啟方式

  - 依是不是 PWA。
  - PWA 或窄版在同一個畫面開啟。

## 做法要點

- 這個 plan 只改前端，沒有 API、資料庫或部署順序的變更，也不改法律頁面的文字。
- 窄版的判斷寫成一個 media query：`(width < 600px), (height < 480px)`。SCSS 的 mixin 與 `utils/mediaQuery.ts` 用同一個定義，跟 plan 0011 讓 TypeScript 與 SCSS 在同一個像素切換的做法一致。用途字級的 token 改在這個 query 切換，不再在 `lg` 切換；斷點表目前沒有 600px，實作時決定怎麼加進 `styles/tokens/`。
- 前端用 `(hover: hover)` 判斷能不能用滑鼠移入，長按只在窄版而且是觸控事件時生效；是不是 PWA 用現有的 `Util.isPWA` 判斷。
- `architecture.md` 要一起更新：
  - 功能與程式碼對照表的「桌面前台側邊欄」改成「前台導覽」，連到 `navigation.md`。
  - 「手機上的 `Main` 用整頁捲動」這類描述改成窄版，`Main` 與 `Settings` 依窄版決定整頁捲動與 `body` 的 class。`Main` 選捲動容器的 `getScrollContainer` 與 `getPageScrollContainer` 現在依 780px 與 960px 選，要跟整頁捲動的判斷一致，可用寬度在 600 到 779px 之間，或可用高度小於 480px 時也要選對容器，歷史紀錄頁捲到底時才會照 REC-R16 載入更多紀錄。
  - 功能與程式碼對照表裡「桌面瀏覽器的搜尋視窗」這類依裝置寫的描述，改成依窄版與寬版寫。
  - 記下實機測過的行為（見下一項）。
- 實作要在實機確認下面的結果，並把測過的行為寫進 `architecture.md`：
  - iPad 的 Safari 直立時是寬版、顯示圖示列，橫放時顯示展開的側邊欄。
  - iPhone 橫放時是窄版。
  - iOS Safari、iOS 的 PWA 與 Android Chrome 上，鍵盤彈出時版面不會在窄版與寬版之間切換。

    `index.html` 的 viewport 沒有設定 `interactive-widget`，照瀏覽器的預設，鍵盤彈出時不會改變 layout viewport 的高度，不過這一點還沒實測。如果版面會切換，實作要讓版面在輸入框有焦點時維持原樣。
  - iOS Safari 允許雙指縮放時，版面不因雙指縮放在窄版與寬版之間切換；iOS 的 PWA 會不會允許雙指縮放，照實測記下。
  - 視窗跨過窄版與寬版的分界時，已經開著的編輯器視窗或編輯頁保留使用者填好的內容。
  - iPad 這類寬版的觸控裝置長按清單的一列時，不出現 bottom sheet，放開手指之後跟點一下一樣開啟這一筆的編輯器，也不跳出文字選取或系統的選單。

    iPadOS Safari 長按之後會不會送出 click 還沒實測，實作照實測的結果處理並記下。
  - 訪客在 LINE 這類 App 內建的瀏覽器點歡迎頁的法律頁面連結時，看完之後能回到歡迎頁。

    這些瀏覽器怎麼處理開新分頁的連結還沒實測，實作要實測並記下。
- `tests/manual/navigation.md` 的標題也改成「前台導覽」。這個 plan 改了名稱的情境，`tests/manual/` 裡的小節標題要一起改，`make check-scenarios` 才會通過。
- `ui-guidelines.md` 的「版面」、雙指縮放與字級的設計理由現在連到 `docs/plans/0012-width-based-layout.md`，實作把 plan 移到 `docs/plans/archive/` 時，同時把這些連結改成 archive 的路徑。
- 現有的 Vitest test 都在 jsdom 的 User-Agent 下執行，`Util.isMobile` 在這個 User-Agent 下回傳 false，所以測試跑的都是桌面版；改成依 media query 判斷之後，依版面而不同的測試要 mock `matchMedia`，例如 `RecordEditor.test.tsx` 現有的 `mockViewport` 要改用窄版的新 query。
