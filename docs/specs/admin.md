# 後台

後台讓開發者知道有多少使用者在使用 Taigu、新使用者會不會持續使用，以及試用後有多少使用者付費訂閱，並處理使用者的問題回報。只有 superuser 能使用後台，後台在 `/admin` 底下分成三頁：使用情況頁 `/admin/usage`、訂閱頁 `/admin/subscriptions` 與問題回報頁 `/admin/issue-reports`。

## 需求

### ADMIN-R1 只有 Superuser 能使用後台

只有 superuser 能開啟 `/admin` 底下的頁面，也只有 superuser 能讀取或修改後台的資料。開啟後台或讀取後台的資料時，依以下規則處理：

- Superuser 開啟 `/admin` 時，畫面換到導覽的第一頁，也就是使用情況頁 `/admin/usage`，瀏覽紀錄裡的 `/admin` 被使用情況頁取代。
- 已登入但不是 superuser 的使用者開啟 `/admin` 底下的網址時，畫面在原本的網址顯示 404 頁面（見 PUB-R5）。
- 已登入但不是 superuser 的使用者不經過畫面、直接送出讀取或修改後台資料的 request 時，後端拒絕這個 request，回應跟 request 送到不存在的網址時相同，而且使用者的登入狀態不變。
- 未登入的使用者開啟後台的網址時，處理方式見 ACCT-R3。

- ADMIN-R1.1 Superuser 開啟後台
  - 前提：使用者是 superuser，已經登入。
  - 動作：開啟 `/admin`。
  - 結果：網址換成 `/admin/usage`，畫面顯示使用情況頁。
- ADMIN-R1.2 不是 superuser 的使用者開啟後台
  - 前提：使用者已經登入，不是 superuser。
  - 動作：開啟 `/admin/usage`。
  - 結果：網址維持 `/admin/usage`，畫面顯示 404 頁面，標題是「找不到頁面」。
- ADMIN-R1.3 不是 superuser 的使用者直接讀取後台的資料
  - 前提：使用者已經登入，不是 superuser。
  - 動作：不經過畫面，直接向後端送出讀取問題回報列表的 request，接著開啟設定頁 `/settings`。
  - 結果：後端拒絕讀取問題回報列表的 request，不回傳任何問題回報，回應的 status code 與內容跟 request 送到不存在的網址（例如 `/api/does-not-exist`）時相同；設定頁照常顯示這位使用者的名字與 Email，使用者沒有被登出。
- ADMIN-R1.4 未登入時開啟後台
  - 前提：使用者是 superuser，沒有登入。
  - 動作：開啟 `/admin/usage`，畫面換到歡迎頁之後，在原分頁從記住網址起算未滿 30 分鐘時，用 Google 帳號完成登入。
  - 結果：畫面換到 `/admin/usage`，顯示使用情況頁。
- ADMIN-R1.5 取消 superuser 之後重新整理
  - 前提：使用者是 superuser，開著使用情況頁 `/admin/usage`，之後開發者取消了這位使用者的 superuser。
  - 動作：重新整理頁面。
  - 結果：網址維持 `/admin/usage`，畫面顯示 404 頁面。
- ADMIN-R1.6 Access token 過期之後操作後台
  - 前提：Superuser 在登入滿 30 天之前開著問題回報頁的「未處理」，最後取得的 access token 已經過期。
  - 動作：點一則問題回報的勾選按鈕。
  - 結果：畫面出現提示「已標記為已處理。」，這則問題回報從列表消失，superuser 沒有被登出。

### ADMIN-R2 設定與取消 Superuser

開發者可以依 email 把 Taigu 的使用者設成 superuser、取消 superuser，以及列出所有 superuser 的 email。輸入的 email 找不到 Taigu 的帳號時，開發者看到錯誤訊息，後端不改變任何帳號。使用者更換綁定的 Google 帳號（見 ACCT-R11）之後仍是 superuser。

- ADMIN-R2.1 設成 superuser
  - 前提：Email 是 `dev@example.com` 的使用者不是 superuser。
  - 動作：開發者把 `dev@example.com` 設成 superuser，這位使用者再開啟 `/admin/usage`。
  - 結果：畫面顯示使用情況頁。
- ADMIN-R2.2 取消 superuser
  - 前提：Email 是 `dev@example.com` 的使用者是 superuser。
  - 動作：開發者取消 `dev@example.com` 的 superuser，這位使用者再開啟 `/admin/usage`。
  - 結果：畫面顯示 404 頁面。
- ADMIN-R2.3 Email 找不到帳號
  - 前提：沒有任何 Taigu 帳號的 email 是 `nobody@example.com`。
  - 動作：開發者把 `nobody@example.com` 設成 superuser。
  - 結果：開發者看到錯誤訊息，所有帳號的 superuser 都沒有改變。
- ADMIN-R2.4 列出 superuser
  - 前提：Email 是 `dev@example.com` 與 `ops@example.com` 的使用者是 superuser，其他使用者都不是。
  - 動作：開發者列出所有 superuser。
  - 結果：列出的 email 只有 `dev@example.com` 與 `ops@example.com`。
- ADMIN-R2.5 更換綁定的 Google 帳號
  - 前提：使用者是 superuser。
  - 動作：使用者把綁定的 Google 帳號換成另一個 Google 帳號，再開啟 `/admin/usage`。
  - 結果：畫面顯示使用情況頁。

### ADMIN-R3 設定頁的後台入口

Superuser 的設定頁 `/settings` 有「管理」區塊，裡面只有連到後台 `/admin` 的「後台」；不是 superuser 的使用者，設定頁沒有「管理」區塊。

- ADMIN-R3.1 Superuser 從設定頁進入後台
  - 前提：使用者是 superuser，已經登入。
  - 動作：開啟設定頁 `/settings`，點「管理」區塊的「後台」。
  - 結果：網址換成 `/admin/usage`，畫面顯示使用情況頁。
- ADMIN-R3.2 不是 superuser 的使用者開啟設定頁
  - 前提：使用者已經登入，不是 superuser。
  - 動作：開啟設定頁 `/settings`。
  - 結果：設定頁沒有「管理」區塊，也沒有「後台」。
- ADMIN-R3.3 從後台按上一頁回到設定頁
  - 前提：Superuser 在設定頁 `/settings` 點「管理」區塊的「後台」，畫面顯示使用情況頁。
  - 動作：按瀏覽器的上一頁。
  - 結果：網址換回 `/settings`，畫面顯示設定頁。

### ADMIN-R4 後台的導覽

後台的每一頁都有導覽，列出「使用情況」「訂閱」「問題回報」三頁與「回到 Taigu」，目前所在的頁面在導覽上顯示成選取狀態，點「回到 Taigu」時畫面換到儀表板 `/`。有未處理的問題回報（見 ADMIN-R13）時，導覽的「問題回報」旁邊顯示未處理的則數；沒有未處理的問題回報時不顯示則數。後台的頁面不顯示 Taigu 的側邊欄與底部導覽列。

導覽在寬的視窗裡是左側的側邊欄，側邊欄可以收合成只剩圖示：收合時，指到圖示會顯示頁面的名稱，未處理的則數顯示在「問題回報」圖示的右上角。前端把收合或展開的狀態記在這個瀏覽器裡，之後開啟後台時維持同樣的狀態，第一次開啟時是展開的。導覽在窄的視窗裡放在畫面上方，不能收合，也不受側邊欄收合狀態的影響，「回到 Taigu」只顯示房子的圖示（版面見 ui-guidelines.md 的「後台」）。

- ADMIN-R4.1 有未處理的問題回報
  - 前提：Superuser 已經登入，有 3 則未處理與 2 則已處理的問題回報。
  - 動作：開啟使用情況頁 `/admin/usage`。
  - 結果：導覽的「使用情況」顯示成選取狀態，「問題回報」旁邊顯示 3。
- ADMIN-R4.2 沒有未處理的問題回報
  - 前提：Superuser 已經登入，問題回報都已經處理。
  - 動作：開啟使用情況頁 `/admin/usage`。
  - 結果：導覽的「問題回報」旁邊沒有顯示則數。
- ADMIN-R4.3 回到 Taigu
  - 前提：Superuser 開著訂閱頁 `/admin/subscriptions`。
  - 動作：點導覽的「回到 Taigu」。
  - 結果：網址換成 `/`，畫面顯示儀表板。
- ADMIN-R4.4 收合側邊欄
  - 前提：Superuser 在桌面瀏覽器上開著問題回報頁，側邊欄是展開的，有 3 則未處理的問題回報。
  - 動作：點側邊欄頂端的收合按鈕，再把滑鼠移到「訂閱」的圖示上。
  - 結果：側邊欄只剩圖示，「問題回報」圖示的右上角顯示 3；滑鼠指到的圖示旁顯示「訂閱」。
- ADMIN-R4.5 再次開啟後台時維持收合
  - 前提：Superuser 在桌面瀏覽器上把側邊欄收合之後，關閉了後台的分頁。
  - 動作：在同一個瀏覽器裡再開啟 `/admin/usage`。
  - 結果：側邊欄是收合的。
- ADMIN-R4.6 收合之後把視窗拉窄
  - 前提：Superuser 在桌面瀏覽器上開著使用情況頁，側邊欄是收合的。
  - 動作：把視窗拉窄到導覽移到畫面上方，再拉寬。
  - 結果：視窗窄的時候，上方的導覽列出「使用情況」「訂閱」「問題回報」三頁的名稱；拉寬之後，側邊欄仍是收合的。
- ADMIN-R4.7 第一次開啟後台
  - 前提：Superuser 在這個桌面瀏覽器上從來沒有開啟過後台。
  - 動作：開啟 `/admin/usage`。
  - 結果：側邊欄是展開的。

### ADMIN-R5 統計的計算方式

後台的統計都依下面的定義計算：

- 一天、一週與一個月都以台灣時間計算，一週從週一到週日。
- 使用者在某一天有使用紀錄（見 USAGE-R1），就算這一天活躍，不論使用紀錄是哪個平台，也包括沒有記下平台的使用紀錄。
- 使用者的註冊日是後端替這位使用者建立帳號（見 ACCT-R2）的那一天。
- 使用紀錄開始的那天，是所有使用紀錄裡最早的日期；還沒有任何使用紀錄時，沒有使用紀錄開始的那天。
- Superuser 與白名單上的使用者照樣算進統計，例外見 ADMIN-R9。
- 後端在 superuser 開啟頁面時用當下的資料計算統計，所以帳號已經刪除的使用者不算進任何一天的統計，包括帳號刪除之前的日子。

- ADMIN-R5.1 同一天在不同平台使用
  - 前提：Superuser 在 2026/12/10 開啟使用情況頁；使用者 A 在 2026/12/09 有網頁、PWA 與沒有記下平台的使用紀錄各一筆，其他使用者在 2026/12/09 都沒有使用紀錄。
  - 動作：看使用情況頁的每日活躍人數。
  - 結果：每日活躍人數是 1 人。
- ADMIN-R5.2 註冊日以台灣時間計算
  - 前提：使用紀錄開始的那天是 2026/12/01。後端在 UTC 2026/12/08 17:30（台灣時間 2026/12/09 01:30）替使用者 B 建立帳號，2026/12/08 與 2026/12/09 都沒有其他人註冊。
  - 動作：Superuser 在 2026/12/10 開啟使用情況頁，看新註冊人數的圖。
  - 結果：2026/12/09 的新註冊人數是 1 人，2026/12/08 是 0 人。
- ADMIN-R5.3 帳號刪除之後
  - 前提：2026/12/01 只有使用者 A 與使用者 C 有使用紀錄，開發者在 2026/12/05 依使用者 A 的要求刪除了 A 的帳號。
  - 動作：Superuser 在 2026/12/10 開啟使用情況頁，看活躍人數的圖上 2026/12/01 的每日活躍人數。
  - 結果：2026/12/01 的每日活躍人數是 1 人。
- ADMIN-R5.4 Superuser 也算進統計
  - 前提：2026/12/09 只有一位 superuser 有使用紀錄。
  - 動作：這位 superuser 在 2026/12/10 開啟使用情況頁。
  - 結果：每日活躍人數是 1 人。

> 設計理由：沒有記下平台的使用紀錄照常算成活躍，而不是排除或併進同一天有平台的那一筆，因為活躍人數依使用者與日期去重，沒有記下平台的那一筆不會讓人數重複算；排除的話，使用者只用過舊版前端的那幾天，活躍人數會少算這位使用者。完整討論見 [0004](../plans/archive/0004-admin-console.md)。

### ADMIN-R6 使用情況頁的摘要數字

使用情況頁最上方顯示四個數字：昨天的每日活躍人數（DAU）、到昨天為止 7 天的活躍人數（WAU）、到昨天為止 30 天的活躍人數（MAU），以及到昨天為止的累計註冊人數。N 天的活躍人數是這 N 天裡至少活躍一天的使用者人數。每個數字底下顯示這個數字比 7 天前同一天增加或減少多少人，人數後面都寫「人」：

- 增加時用紅色寫「▲ +」與增加的人數。
- 減少時用綠色寫「▼ −」與減少的人數。
- 沒有變化時寫「±0 人」。

三個活躍人數另有以下規則，累計註冊人數不受這些規則影響：

- 還沒有任何使用紀錄，或昨天早於使用紀錄開始的那天時，三個活躍人數的位置都只顯示「尚未開始記錄」。
- 7 天前同一天早於使用紀錄開始的那天時，三個活躍人數都不顯示增減。

> 設計理由：區間有一部分早於使用紀錄開始的那天時，摘要數字照常顯示，不另外標示，因為這只發生在使用紀錄開始後的前 30 天，活躍人數的圖也已經把這段期間標成資料不完整。完整討論見 [0004](../plans/archive/0004-admin-console.md)。

- ADMIN-R6.1 四個數字
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/11/01。使用者 A 在 2026/12/09 有使用紀錄，使用者 B 在 2026/12/09 與 2026/12/04 有使用紀錄，使用者 C 在 2026/12/04 有使用紀錄，使用者 D 在 2026/11/12 有使用紀錄，使用者 E 在 2026/11/01 有使用紀錄，其他使用者都沒有使用紀錄；到 2026/12/09 為止有 412 位使用者註冊。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：每日活躍人數是 2 人，7 天的活躍人數是 3 人，30 天的活躍人數是 4 人，累計註冊人數是 412 人。
- ADMIN-R6.2 今天的使用不算進摘要數字
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/11/01。2026/11/10 到 2026/12/10 之間，只有使用者 A 在 2026/12/09 與 2026/12/10 有使用紀錄，以及使用者 F 在 2026/12/10 有使用紀錄；到 2026/12/09 為止有 412 位使用者註冊，使用者 F 在 2026/12/10 註冊。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：每日活躍人數、7 天與 30 天的活躍人數都是 1 人，累計註冊人數是 412 人。
- ADMIN-R6.3 跟 7 天前相比減少
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/11/01，2026/12/02 的每日活躍人數是 5 人，2026/12/09 是 2 人。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：每日活躍人數底下用綠色寫「▼ −3 人」。
- ADMIN-R6.4 跟 7 天前相比沒有變化
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/11/01，2026/12/02 與 2026/12/09 的每日活躍人數都是 2 人。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：每日活躍人數底下寫「±0 人」。
- ADMIN-R6.5 昨天早於使用紀錄開始的那天
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/12/10。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：三個活躍人數的位置都顯示「尚未開始記錄」，累計註冊人數照常顯示人數與增減。
- ADMIN-R6.6 還沒有任何使用紀錄
  - 前提：還沒有任何使用紀錄。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：三個活躍人數的位置都顯示「尚未開始記錄」，累計註冊人數照常顯示人數與增減。
- ADMIN-R6.7 昨天就是使用紀錄開始的那天
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/12/09，使用者 A 在 2026/12/09 有使用紀錄。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：三個活躍人數都是 1 人，底下都沒有增減。
- ADMIN-R6.8 7 天前同一天早於使用紀錄開始的那天
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/12/05。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：三個活躍人數照常顯示，底下都沒有增減；累計註冊人數底下照常顯示增減。
- ADMIN-R6.9 7 天前同一天就是使用紀錄開始的那天
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/12/02。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：三個活躍人數底下都顯示增減。
- ADMIN-R6.10 區間有一部分早於使用紀錄開始的那天
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/12/01。使用者 A 在 2026/12/01 有使用紀錄，使用者 B 在 2026/12/09 有使用紀錄，沒有其他使用紀錄。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：30 天的活躍人數是 2 人，沒有另外的標示。
- ADMIN-R6.11 跟 7 天前相比增加
  - 前提：今天是 2026/12/10，使用紀錄開始的那天是 2026/11/01，2026/12/02 的每日活躍人數是 2 人，2026/12/09 是 5 人。
  - 動作：Superuser 開啟使用情況頁。
  - 結果：每日活躍人數底下用紅色寫「▲ +3 人」。

> 設計理由：每週與每月的活躍人數用往前 7 天與 30 天的區間計算，而不是週一到週日、1 日到月底，因為日曆月在月初只累積了幾天，活躍人數會偏低，而往前 7 天與 30 天的區間每天都包含完整的 7 天或 30 天。區間用 30 天而不是 GA4 的 28 天，因為開發者對「每月」的理解比較接近 30 天。摘要數字顯示昨天而不是今天，因為今天還沒過完，早上看到的數字一定偏低；增減跟 7 天前同一天比，因為平日與週末的使用量不同，跟前一天比的增減大多來自星期幾不同。完整討論見 [0004](../plans/archive/0004-admin-console.md)。

### ADMIN-R7 活躍人數與新註冊人數的圖

### ADMIN-R9 試用轉付費

訂閱頁有試用轉付費表，依試用期開始的月份把使用者分批。現在在白名單上的使用者，以及後端沒有記下試用期的使用者，不算進任何一批。

> 設計理由：試用轉付費不算白名單上的使用者，雖然後台的其他統計都包括他們（見 ADMIN-R5），因為白名單上的使用者不用付費就能使用 Standard，算進試用人數只會讓轉換率隨開發者加進白名單的人數變低；白名單只記下目前誰在白名單上，沒有加入與移出的歷史，所以依現在的白名單判斷。完整討論見 [0004](../plans/archive/0004-admin-console.md)。

表格列出從最早有人算進的月份到本月的每一個月，新的月份排在上面，每一列顯示：

- 試用開始的月份。
- 試用人數：試用期在這個月開始、算進這一批的人數。
- 付款人數：這一批裡，第一次付款成功（見 BILL-R14）的時間不晚於試用期結束後 30 天的人數，在試用期間付款的使用者也算。試用期的結束時間一律用後端記下的結束時間，使用者在試用期間付款時也一樣。
- 轉換率：付款人數除以試用人數，四捨五入到小數 1 位的百分比。
- 狀態：這一批的結算時間是這個月最後一天的隔天 0 點再過 61 天（31 天的試用期加 30 天），在這個時間之前，這一批的付款人數還會變，所以狀態顯示「進行中」與「<結算時間前一天的月/日> 結算」；到了這個時間之後，狀態顯示「已結算」。這個月還沒過完時，結算時間也照同樣的方式計算。

訂閱頁顯示五種訂閱狀態（見 billing.md 的開頭）各有幾位使用者，以及白名單上的使用者人數，白名單上的使用者也依各自的訂閱狀態算進五種狀態的人數。後端依目前記下的訂閱狀態計算人數，記下的狀態可能比 billing.md 開頭的狀態圖晚改變：

- 試用期或已停止自動續訂的本期結束之後，要等下一次每天的到期處理執行，記下的狀態才會改變。
- 自動續訂中的本期結束之後，要等本期結束滿 1 天之後的那一次每天的到期處理執行，記下的狀態才會改變（見 BILL-R22）。
- 不過試用期結束的使用者在每天的到期處理執行之前再操作 Taigu 時，例如登入、開啟或重新整理頁面（包括後台的頁面）、在設定頁以外的頁面之間換頁、開啟方案頁，或新增交易紀錄、現金股利、買賣計畫與自選股，記下的狀態在那時就變成未訂閱；只切回一直開著的分頁、沒有其他操作時，記下的狀態不變。

後端沒有記下訂閱狀態的使用者，也就是計費功能上線之前註冊、上線之後沒有再開啟過 Taigu 的使用者，算成未訂閱。

### ADMIN-R12 問題回報列表

問題回報頁列出問題回報，送出時間新的排在上面。開啟時只列未處理的問題回報（見 ADMIN-R13），可以用「未處理」與「全部」切換。列表一次載入 10 則；目前的篩選（未處理或全部）裡，還有比列表最後一則更早送出的問題回報時，最下面有「載入更多」，點了再載入同一個篩選裡比最後一則更早送出的 10 則。每則問題回報顯示：

- 送出的使用者的 email、送出時的平台（網頁或 PWA，沒有記下平台時寫「平台未記錄」）與送出的時間（台灣時間）。
- 內容依目前的寬度顯示，最多顯示 4 行。內容超過 4 行時有「展開全文與 User-Agent」，沒有超過時有「顯示 User-Agent」；點這兩個按鈕的任何一個之後，畫面顯示完整的內容與 User-Agent（沒有記下或記下的是空字串時寫「User-Agent 未記錄」），點「收合」之後恢復成最多 4 行。
- 右側有圓形的勾選按鈕，未處理的問題回報是空心的圓圈，已處理的問題回報是打勾的實心圓圈（見 ADMIN-R13）。

內容一律當成純文字顯示。沒有可以列出的問題回報時，「未處理」顯示「沒有未處理的問題回報。」，「全部」顯示「還沒有人送出問題回報。」。

### ADMIN-R13 標記問題回報已處理

新送出的問題回報都是未處理。每則問題回報的勾選按鈕（見 ADMIN-R12）用來切換這則問題回報是否已處理。指到按鈕時，畫面顯示按鈕的動作，未處理時是「標記為已處理」，已處理時是「改回未處理」。點勾選按鈕時依以下規則處理：

- Superuser 點未處理的問題回報的勾選按鈕時，這則問題回報變成已處理，畫面出現提示「已標記為已處理。」，導覽上未處理的則數（見 ADMIN-R4）少 1，而且在「未處理」的列表裡不再顯示這則問題回報。
- Superuser 點已處理的問題回報的勾選按鈕時，這則問題回報變回未處理，畫面出現提示「已改回未處理。」，未處理的則數多 1。
- 點了勾選按鈕之後，後端回應之前，這顆按鈕顯示成處理中，不能再點。
- 標記沒有成功時，除了登入狀態結束的情況（處理方式見 ACCT-R5），畫面出現錯誤提示「無法更新這則問題回報，請稍後再試。」，問題回報維持原本的狀態。

- ADMIN-R13.1 標記為已處理
  - 前提：有 3 則未處理的問題回報，superuser 開著問題回報頁的「未處理」。
  - 動作：點最上面那則問題回報的勾選按鈕。
  - 結果：畫面出現提示「已標記為已處理。」，列表剩下 2 則問題回報，導覽的「問題回報」旁邊顯示 2。
- ADMIN-R13.2 改回未處理
  - 前提：有 2 則未處理與 1 則已處理的問題回報，superuser 開著問題回報頁的「全部」。
  - 動作：點已處理的那則問題回報的勾選按鈕。
  - 結果：畫面出現提示「已改回未處理。」，這則問題回報的勾選按鈕變回空心的圓圈，導覽的「問題回報」旁邊顯示 3。
- ADMIN-R13.3 新送出的問題回報
  - 前提：問題回報都已經處理。
  - 動作：使用者送出一則問題回報（見 ISSUE-R3），superuser 再開啟問題回報頁。
  - 結果：列表列出剛送出的那則問題回報，導覽的「問題回報」旁邊顯示 1。
- ADMIN-R13.4 網路中斷時標記
  - 前提：Superuser 開著問題回報頁的「未處理」，裝置的網路中斷。
  - 動作：點一則問題回報的勾選按鈕。
  - 結果：畫面出現錯誤提示「無法更新這則問題回報，請稍後再試。」，這則問題回報仍在列表裡，勾選按鈕仍是空心的圓圈，導覽上的則數不變。
- ADMIN-R13.5 指到勾選按鈕
  - 前提：有 1 則未處理與 1 則已處理的問題回報，superuser 在桌面瀏覽器上開著問題回報頁的「全部」。
  - 動作：把滑鼠移到未處理那則的勾選按鈕上，再移到已處理那則的勾選按鈕上。
  - 結果：未處理那則顯示「標記為已處理」，已處理那則顯示「改回未處理」。
- ADMIN-R13.6 回應之前再點一次
  - 前提：Superuser 開著問題回報頁的「全部」，網路很慢。
  - 動作：點一則未處理的問題回報的勾選按鈕，在後端回應之前再點一次。
  - 結果：第一次點之後按鈕顯示成處理中，第二次點沒有作用；回應之後畫面出現提示「已標記為已處理。」，這則問題回報的勾選按鈕是打勾的實心圓圈。
- ADMIN-R13.7 標記最後一則未處理的回報
  - 前提：只有 1 則未處理的問題回報，superuser 開著問題回報頁的「未處理」。
  - 動作：點這則問題回報的勾選按鈕。
  - 結果：畫面出現提示「已標記為已處理。」，列表的位置顯示「沒有未處理的問題回報。」，導覽的「問題回報」旁邊不再顯示則數。

### ADMIN-R14 讀取失敗

後台的頁面讀取資料失敗時，除了登入狀態結束的情況（處理方式見 ACCT-R5），畫面在原本要顯示資料的地方顯示「無法載入資料。」與「重新載入」，點「重新載入」時再讀取一次。

- ADMIN-R14.1 網路中斷時開啟使用情況頁
  - 前提：Superuser 已經登入，裝置的網路中斷。
  - 動作：在後台裡換到使用情況頁，網路恢復之後點「重新載入」。
  - 結果：換到使用情況頁時，畫面顯示「無法載入資料。」與「重新載入」；點了之後畫面顯示使用情況頁的數字、圖與留存表。
